## 一、真实问题分析

### 1.1 表面需求

用户原话（从 idea.txt 提取）：

> "成长徽章页面显示已获得徽章/待获得徽章/成长报告——说实话我还没有想好"

用户表达了明确的意图（需要徽章激励体系）但对具体设计没有预设方案。结合已确认的上下文：
- 首页右侧边栏有微缩徽章入口（已确认）
- 打卡连续里程碑会触发徽章奖励（已确认：3/7/30/100 天）
- 花园交互中收集徽章（已确认）
- 徽章页面独立存在（已确认）

### 1.2 真实问题（3层Why追问）

| 层级        | 追问                             | 回答 |
| ----------- | -------------------------------- | ---- |
| 第 1 层 Why | 为什么需要徽章体系？             | 花园探索提供"玩"的动机，每日打卡提供"来"的动机，但缺少一个让孩子"想做得更好"的长期激励——徽章体系填补了这个空缺，将零散的打卡和交互行为串联为有意义的"成就叙事" |
| 第 2 层 Why | 为什么简单的积分/星星不够？      | 3-6 岁儿童对"收集"有天然痴迷（参考贴纸、扭蛋、宝可梦卡牌的心理机制）；徽章的视觉化、稀有度分级和"待获得"的预告，比抽象积分更能激发内在驱动力；家长也能通过徽章直观看到孩子的成长轨迹 |
| 第 3 层 Why | 如果不做徽章，最严重的后果是什么？ | 打卡变成纯粹的"任务清单"，孩子一周后失去新鲜感；家长看不到累积价值，留存曲线在第 7-14 天断崖式下跌；花园中的行为（投喂、探索、科普问答）缺少"被记住"的痕迹 |

**结论**：真正要解决的问题是——**为 3-6 岁儿童构建一套可视化、可收集的成就叙事系统，让每一次交互（打卡、探索、学习）都被"铸造成一枚徽章"，形成"今天做了什么 → 获得什么 → 还想获得什么"的正向循环，同时为家长提供一目了然的成长轨迹。**

### 1.3 解法空间

| 解法 | 描述 | 优势 | 劣势 | 可行性评估 |
| ---- | ---- | ---- | ---- | ---------- |
| 方案 A：徽章 + 等级体系（推荐） | 徽章分 4 种分类 × 3 级稀有度，获得徽章累积"花园经验值"提升花园等级，解锁新区域/角色 | 双重激励（收集欲 + 成长感）、体系完整、与花园深度联动 | 设计复杂度较高，徽章数量和获取规则需精心平衡 | 高 |
| 方案 B：仅徽章（无等级） | 纯徽章收集系统，不设整体等级，徽章之间平级无稀有度 | 实现简单、用户理解成本低 | 缺少"下一步"的引导感，长期激励不足 | 高 |
| 方案 C：积分排行榜 | 所有行为累计积分，展示家庭内/好友间排名 | 社交竞争驱动 | 3-6 岁不适合竞争排名、家长隐私顾虑、与产品"温暖陪伴"调性冲突 | 低 |

**选定方案**：**方案 A（徽章 + 等级体系）**，理由：
- 收集（徽章）满足短周期成就感，等级（花园进化）满足长周期成长感，两者互补
- 等级直接联动花园场景变化（如 Lv.3 解锁新区域），让徽章不是"静态贴纸"而是"改变世界的钥匙"
- 3-6 岁儿童对"升级"概念已有认知（受游戏/动画影响），不需要引入排名竞争

| BD-07 | 查看成长报告（家长） | 家长在徽章页面切换到"成长报告"Tab，查看周期性的消化健康趋势和习惯统计 | 中 | **P1** | 家长留存的关键 |

| BD-09 | 徽章升级（铜→银→金） | 同一徽章类别内满足更高阶条件时，徽章从铜升级为银/金 | 低 | **P1** | 同一成就的深度递进 |

### 3.2 优先级判定

- **P0（必须支持）**：BD-01 获得徽章、BD-02 获得动画、BD-03 浏览已获得、BD-04 浏览待获得。这是徽章体系的最小闭环。
- **P1（应当支持）**：BD-05 花园等级、BD-06 等级升级、BD-07 成长报告、BD-09 徽章升级。完整激励体系的必要组成。
- **P2（可以延后）**：BD-08 徽章分享。社交传播类，不影响核心体验。

## 四、业务流程梳理

### 4.1 主流程（Happy Path） — BD-01/02 获得新徽章

| 步骤 | 操作者 | 动作 | 系统判断 | 输入 | 输出 | 状态变化 |
| ---- | ------ | ---- | -------- | ---- | ---- | -------- |
| 1 | 用户 | 完成某个触发行为（如连续打卡 7 天） | — | 行为事件 | — | — |
| 2 | 系统 | 检测到条件满足 → 查询该徽章是否已获得 | 已获得且未达升级条件 → 不触发；未获得 → 触发 BD-02 | 用户行为日志 + 徽章条件规则 | 判断结果 | 徽章待发放 |
| 3 | 系统 | 发放徽章 + 触发全屏揭晓动画 | — | 徽章数据 | 动画（徽章旋转/发光/音效）+ 徽章名称和描述文案 | 徽章状态：待获得 → 已获得 |
| 4 | 系统 | 累积花园经验值，检查是否触发等级升级 | 经验值 ≥ 下一级阈值 → 触发 BD-06 | 徽章经验值 | 等级进度条更新 / 等级升级动画 | 经验值增加 |
| 5 | 系统 | 在首页右侧边栏微缩区域显示最新徽章角标 | — | — | 首页微缩徽章区出现"NEW"角标 | 首页 UI 更新 |
| 6 | 用户 | （可选）点击角标或进入徽章页面查看新徽章详情 | — | 点击事件 | 徽章详情（大图 + 获得日期 + 获得条件描述） | — |

### 4.2 状态机 — 徽章生命周期

```
          ┌──────────────────┐
          │   未获得（灰色）  │ ← 所有徽章初始状态
          │   显示获取条件    │
          └────────┬─────────┘
                   │ 行为满足获取条件
                   ▼
          ┌──────────────────┐
          │   已获得（铜）    │ → 徽章亮起 + 揭晓动画 + 经验值
          └────────┬─────────┘
                   │ 满足升级条件（如累积打卡 30 天）
                   ▼
          ┌──────────────────┐
          │   已升级（银）    │ → 徽章边框变化 + 升级动画 + 额外经验
          └────────┬─────────┘
                   │ 满足进阶条件（如累积打卡 100 天）
                   ▼
          ┌──────────────────┐
          │   已升级（金）    │ → 徽章最高级 + 特殊光效 + 稀有成就
          └──────────────────┘
```

| 当前状态 | 触发事件 | 目标状态 | 条件/约束 |
| -------- | -------- | -------- | --------- |
| 未获得 | 首次满足获取条件 | 已获得（铜） | 行为验证通过，同一徽章不可重复获得 |
| 已获得（铜） | 满足银级升级条件 | 已升级（银） | 需累积满足更高级别条件（如 7 天→30 天） |
| 已获得（银） | 满足金级升级条件 | 已升级（金） | 需累积满足最高级别条件（如 30 天→100 天） |
| 已升级（金） | — | 终态（不再变化） | 金级为最高等级 |

### 4.3 花园等级状态机

```
花园 Lv.1（初始）→ Lv.2（50 XP）→ Lv.3（120 XP）→ Lv.4（220 XP）→ Lv.5（350 XP）→ ...
```

| 等级 | 所需累计经验 | 解锁内容 |
| ---- | ------------ | -------- |
| Lv.1 | 0 | 基础花园场景、3 个核心角色、基础投喂交互 |
| Lv.2 | 50 | 解锁"放大镜科普"功能入口 |
| Lv.3 | 120 | 花园新增"发酵工坊"装饰区域 |
| Lv.4 | 220 | 解锁隐藏角色或角色新皮肤 |
| Lv.5 | 350 | 花园新增"绒毛平原"区域扩展 |

## 五、异常和边界场景

### 5.1 异常场景清单

| 编号 | 类别 | 异常场景 | 触发条件 | 预期系统行为 | 影响范围 |
| ---- | ---- | -------- | -------- | ------------ | -------- |
| BD-EX-01 | 用户操作 | 同一行为同时满足多个徽章条件 | 如连续打卡 30 天，同时触发"月度冠军"徽章和"打卡达人"金级升级 | 按徽章优先级排队播放动画，依次弹出（最多 3 个），超出部分静默发放 + 角标提示"获得了 N 个新徽章" | 徽章发放动画 |
| BD-EX-02 | 数据 | 新用户首次进入徽章页面，无任何徽章 | 徽章列表为空 | 展示引导性空状态："探险刚开始！去花园逛逛、完成每日打卡，就能收集到第一枚徽章啦～" + 展示最容易获得的 1-2 个徽章作为引导目标 | 徽章列表页 |
| BD-EX-03 | 数据 | 成长报告中无便便分析数据 | 家长从未上传便便照片 | 消化健康指标区展示"暂无数据，上传便便照片开启健康追踪～"+ 引导按钮跳转到打卡页面上传 | 成长报告 |
| BD-EX-04 | 系统状态 | 徽章发放时网络断开 | 满足条件时刻恰好离线 | 本地暂存发放事件，网络恢复后补发 + 补播动画；服务端以行为日志为准，杜绝重复发放 | 徽章发放 |
| BD-EX-05 | 历史数据 | 徽章体系改版，旧徽章被移除或合并 | 版本升级时徽章定义变更 | 已获得的旧徽章保留在"经典收藏"分区，标注"经典版"；新徽章按新规则独立计算 | 徽章数据 |
| BD-EX-06 | 并发 | 家长和儿童同时查看徽章页面 | 两台设备同账号同时打开徽章页 | 各自独立展示，不存在冲突（只读场景）；新徽章发放后通过 WebSocket/轮询同步更新 | 徽章页面 |
| BD-EX-07 | 权限 | 儿童试图查看成长报告 | 儿童在无监督下切换到"成长报告"Tab | 成长报告 Tab 对儿童视图隐藏（仅家长视图可见），切换需家长验证 | 徽章页面 |
| BD-EX-08 | 后台处理 | 经验值计算错误导致等级异常 | 徽章发放时经验值累加异常 | 定期（每日凌晨）全量重算经验值并校正；发现异常时不回退已解锁内容，仅修正数值 | 花园等级 |

### 6.2 风险与待补充（含评审发现）

#### 模拟需求评审记录

**资深研发视角**：

| # | 尖锐问题 | 评审结论 |
|---| -------- | -------- |
| 1 | 徽章条件检测是实时还是离线批处理？如果"连续打卡 7 天"的条件在用户打卡瞬间就要判断——每天几十万用户的打卡时间分布在 24 小时内，实时检测没问题。但"本周投喂次数 ≥10 次"这种周期统计，用实时还是每日汇总？ | 建议：简单条件（打卡天数、单次行为）实时检测；周期统计条件（本周/本月汇总）用每日凌晨批处理预计算，白天直接读缓存。徽章条件引擎需要支持两种检测模式 |
| 2 | 徽章数据模型怎么设计？30 枚徽章 × 3 级 × 每个用户一条记录——如果用关系型存储，用户量大了 JOIN 查询扛不住。是否考虑玩家档案 JSON 快照？ | 建议：用户徽章状态用 JSON 快照存储在用户档案中（`{badge_id: {status, level, earned_at}}`），徽章定义表（模板）独立存储。读取时一次查询拿到全量，无需 JOIN |
| 3 | 成长报告的"布里斯托类型分布饼图"需要聚合历史便便分析结果——如果用户有 365 天数据，每次打开报告都实时聚合？ | 建议：每日凌晨预聚合每个儿童的指标快照，报告直接读快照。周报/月报用快照组合，避免实时扫全表 |

**测试负责人视角**：

| # | 尖锐问题 | 评审结论 |
|---| -------- | -------- |
| 4 | 徽章条件规则怎么测试？"连续打卡 7 天"的边界——第 6 天漏打卡 + 第 7 天补签，连续天数算 7 还是中断？补签规则直接影响徽章获取逻辑。 | 需在测试前明确补签与连续天数的关系（已在每日打卡分析中确认：补签不中断连续计数）。测试用例需覆盖补签场景下的徽章触发 |

**业务负责人视角**：

| # | 尖锐问题 | 评审结论 |
|---| -------- | -------- |
| 7 | 30 枚徽章是不是太多了？3-6 岁儿童的注意力有限，如果前两周只能拿到 1-2 枚，后面的"待获得"灰蒙蒙一片，会不会反而挫败？ | 建议：MVP 徽章分"速赢"和"长线"两类——前 3 天至少能拿 3 枚速赢徽章（首次打卡、首次投喂、首次便便分析），让儿童快速建立"我能收集"的信心。待获得区默认折叠，只展示最近 3 枚可获取的 |

| 9 | 成长报告对家长的长期价值是什么？如果只是每周看几个数字，3 周后家长也会腻。报告的差异化在哪里？ | 报告的差异化在于"从便便到饮食到花园"的因果链可视化——不是冷冰冰的数字，而是"上周便便偏干（Type 1）→ 菌小园建议多喝水 → 本周改善为 Type 3 → 花园溪流恢复清澈"这样的叙事性报告。这比竞品的纯数据报告更有温度 |

#### 风险汇总

| 最大风险 | 影响 | 应对 |
| -------- | ---- | ---- |
| 徽章数量/节奏设计不当导致激励失效 | 太少没动力，太多不珍惜，太难挫败 | MVP 先上线 18-20 枚（而非 30 枚），速赢型占 1/3；上线后根据获取率数据调优 |
| 徽章条件规则与打卡/便便分析模块耦合过深 | 任一上游模块变更都可能引发徽章 BUG | 徽章条件引擎用事件驱动架构，监听行为事件而非直接读业务表；条件规则独立配置文件 |
| 成长报告的"叙事性"实现成本高 | 从数据自动生成有温度的文字描述，可能涉及 LLM 调用，增加成本和延迟 | MVP 报告用模板化文案（规则匹配 + 填空），不用 LLM；如"上周便便偏干（Type 1 占 60%）→ 建议多喝水 → 本周改善为 Type 3（占 70%），花园溪流恢复清澈！"用 if-else 模板即可实现 |
